# Traveller AI itinerary planner

The existing `/match` page now includes a signed-in traveller planner. It collects one catalogue destination, inclusive start/end dates (today or later; 1–30 days), at least one catalogue interest, and a whole-NAD total trip budget per person. It sends these preferences to Lovable AI only after Generate. Nothing is stored in browser storage or a traveller record. Opening sign-in in another tab keeps the current form in memory.

`plan-safari` verifies the user session, allowed Origin and bounded request before using a backend-only `LOVABLE_API_KEY`. The model selects catalogue safari IDs or flexible days; the server validates every day and reconstructs all displayed titles/descriptions from the factual catalogue. No free-form model facts, prices, accommodation, transfer estimates, deposits or availability reach the UI. Suggested days are inspiration rather than package durations or reservations. The existing Safari Brief link transfers destination/interests/day-count/budget, not generated text or exact dates.

Deploy `supabase/migrations/202610120005_traveller_ai_planner.sql`, then `supabase functions deploy plan-safari` to the connected project. The function's deno.json maps Zod to the installed compatible npm version; deploy with the repository source tree intact because its shared planner imports `src/lib/pelican.ts`. The unfinished 202610120004 email migration is unrelated: do not blindly push every local migration. Cloud currently has a separate Drizzle migration history; inspect live schema/migration history before applying source migrations.

Configure `LOVABLE_API_KEY` and `ENQUIRY_ALLOWED_ORIGINS` in Edge Function secrets, never browser variables. Enable Lovable AI/credits and sign-in/email confirmation settings. The quota RPC allows 3 attempts/hour/account and 100/day across traveller accounts, including failed gateway attempts; staff drafting has its own existing quota. The ledger stores only user UUID/time and prunes older entries. No prompts, budgets or outputs are logged/stored. RLS and revoked grants hide the ledger. This does not prevent abuse by many newly registered accounts; use verified account controls and monitor gateway spend before public rollout.
